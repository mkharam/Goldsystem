# متابعة الصيانة — Repair Tracker

تطبيق مستقل لاستلام قطع الصيانة ومتابعتها وتسليمها، عربي بالكامل (RTL) ومصمَّم
للهاتف أولاً. يعمل في المتصفح وحده ويُستضاف على GitHub Pages، بقاعدة بيانات
Supabase خاصة به.

يتكامل مع نظام المخزون (`jewel-sight-manager`) عبر واجهة واحدة، **وعند تعذّر
الوصول إليها يبقى التطبيق عاملاً بالكامل بالإدخال اليدوي.**

🔗 <https://mkharam.github.io/Goldsystem/>

## الميزات

- **تذاكر صيانة** برقم متسلسل لكل فرع (`R-26-01-0001`) وصور عند الاستلام
- **تعبئة تلقائية** للوزن والعيار بمسح كود القطعة، وبحث الزبون بالهاتف
- **إيصال بـ QR** يُطبع من المتصفح، يفتح صفحة تتبّع عامة بلا تسجيل دخول
- **مسار حالات** مضبوط: مستلمة ← قيد التنفيذ ← جاهزة ← مسلّمة (أو ملغاة)
- **زر إبلاغ عبر واتساب** برسالة جاهزة، مع تسجيل من أبلغ ومتى
- **فحص الوزن عند التسليم** — يقارن بوزن الاستلام ويمنع الإغلاق عند تجاوز
  المسموح إلا بتأكيد صريح وسبب مكتوب
- **لوحة المتأخّرات** لما فات موعده وما زال مفتوحاً

## عزل الفروع

المدير العام (`admin`) يرى تذاكر كل الفروع. المشرف والموظف لا يرون ولا يكتبون إلا
تذاكر **فرعهم**، ويسري ذلك على الصور والسجل والإشعارات وملفات التخزين. مفروض في
سياسات RLS (`can_access_branch`) لا في الواجهة وحدها. موظف بلا فرع مرتبط لا يرى
شيئاً. الزبائن والفروع والموظفون تبقى مقروءة لكل موظف فعّال.

## البنية الأمنية

التطبيق ملف ثابت على GitHub Pages، فلا خادم يملكه ولا يمكنه إخفاء أي مفتاح.
لذلك:

- المتصفح يحمل **المفتاح العلني** فقط (`publishable`)، وهو لا يمنح شيئاً بذاته.
- **سياسات RLS هي الحارس الوحيد للبيانات.** كل صلاحية مشروطة بوجود صف موظف
  **فعّال** مرتبط بالمستخدم الحالي؛ من لا صف له لا يرى شيئاً ولو امتلك حساباً.
- `anon` ممنوع من كل جدول ومن دالة ترقيم التذاكر — تم التحقق من ذلك عملياً.
- ما لا يصحّ وضعه في المتصفح يعيش في دوال الحافة: مفتاح المخزون، وقراءة صفحة
  التتبّع العامة.

> هذا يختلف عمداً عن نظام المخزون: المستودع علني، فكود التطبيق مقروء للجميع،
> وأي خطأ في سياسات RLS يصبح قابلاً للاستغلال مباشرة. أي تعديل على الجداول يجب
> أن يُراجَع من هذه الزاوية.

## دوال الحافة (على مشروع الصيانة)

| الدالة | الغرض | JWT |
| --- | --- | --- |
| `staff-auth` | التحقق من بيانات الموظف لدى المخزون وتهيئة حسابه هنا | لا |
| `inventory-proxy` | يحمل مفتاح المخزون ويمرّر الاستدعاءات بعد التحقق من الموظف | نعم (يدوياً) |
| `track` | صفحة التتبّع العامة: بيانات محدودة + روابط صور موقّعة | لا |

الأسرار المطلوبة على مشروع الصيانة:

```bash
supabase secrets set \
  INVENTORY_API_URL="https://iiyaytfdxfvjcvzlnlpp.supabase.co/functions/v1/repair-api" \
  INVENTORY_API_KEY="<نفس قيمة REPAIR_API_KEY في المخزون>"
```

وعلى مشروع المخزون: `REPAIR_API_KEY` بنفس القيمة (انظر
`jewel-sight-manager/docs/repair-api.md`).

## تسجيل الدخول

الموظف يدخل **بحساب المخزون نفسه**. عند أول دخول تتحقق `staff-auth` من المخزون
ثم تُنشئ له حساباً هنا بالكلمة نفسها؛ بعدها يدخل مباشرة عبر Supabase Auth —
فيبقى الدخول ممكناً حتى لو انقطع المخزون تماماً.

لذلك **يجب ضبط أسرار المخزون قبل أن يتمكّن أول موظف من الدخول.**

## التشغيل محلياً

```bash
npm install
npm run dev     # http://localhost:8080
```

`.env` في المستودع عمداً: لا يحوي إلا عنوان المشروع والمفتاح العلني، وكلاهما
يظهر أصلاً في حزمة المتصفح. **لا يجوز أبداً وضع مفتاح `service_role` فيه.**

## النشر

كل دفعة إلى `main` أو فرع التطوير تبني الموقع وتنشره على GitHub Pages
(`.github/workflows/deploy-pages.yml`). البناء يضبط `GH_PAGES_BASE=/Goldsystem/`
وينسخ `index.html` إلى `404.html` حتى تعمل روابط التتبّع المباشرة عند فتحها من
رمز QR.

## الإعدادات

من جدول `settings` (يعدّلها المديرون فقط):

| المفتاح | الافتراضي | المعنى |
| --- | --- | --- |
| `weight_tolerance_grams` | `0.05` | الفرق المسموح بين وزن الاستلام والتسليم |
| `default_turnaround_days` | `3` | موعد التسليم الافتراضي عند فتح التذكرة |
| `shop_name` | `مجوهرات` | الاسم على الإيصال وصفحة التتبّع |
| `receipt_footer` | … | نص أسفل الإيصال |
